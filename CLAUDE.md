# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

VocabFlow is a SwiftUI iOS app (iOS 17+, Swift 5 mode, dependencies via SPM: `lottie-ios` for the end-of-session confetti, `rive-ios` (`RiveRuntime`) for the Syllie mascot in `Resources/Animations/syllie.riv`) for learning English vocabulary with Vietnamese meanings. Learning sessions, accounts and progress come from the backend (sibling repo `vocab-backend`, contract in its `docs/FRONTEND_FLOW.md`). Practice Lab content is bundled JSON.

## Commands

```sh
# Build
xcodebuild -project VocabFlow.xcodeproj -scheme VocabFlow \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build

# All tests (XCTest)
xcodebuild -project VocabFlow.xcodeproj -scheme VocabFlow \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' test

# One test class / one test method
xcodebuild ... test -only-testing:VocabFlowTests/SessionReducerTests
xcodebuild ... test -only-testing:VocabFlowTests/SessionReducerTests/testStartBeginsLearnAndLearnFlowsToBuild
```

The project uses Xcode file-system synchronized groups (`objectVersion = 77`): new files under `VocabFlow/` or `VocabFlowTests/` are picked up automatically — do not edit `project.pbxproj` to add them.

## Architecture

### Composition and routing
- `App/VocabFlowApp.swift` builds every store once and injects them with `.environment(...)`. Stores are `@Observable @MainActor` classes; views read them via `@Environment(StoreType.self)`. Previews must inject the same set of stores (see the `#Preview` in `AppRootView.swift`) using test doubles (`NoOpFeedback`, `SilentSpeech`, `InMemoryPreferencesStore`, `NoReminders`, `OfflineVocabAPI`, `SilentAudioClips`, `NoVoiceRecorder`, `defaults: nil`).
- There is no `NavigationStack`. `App/AppRootView.swift` derives a single `RouteID` from store state (onboarding → Practice Lab sandbox → session phase) and swaps whole screens with `.id(route)` + a transition. Changing a screen means changing store state, not pushing views.

### Backend session (the live flow)
- `Networking/`: `APIClient` (actor: bearer auth, one refresh-and-retry on 401, backoff), `VocabAPI` (protocol, `LiveVocabAPI`, and `OfflineVocabAPI` for previews). Default server: local backend on the simulator, `https://moneytogether.dpdns.org/service/vocab/` on a real device (`APIConfiguration`). Override with the `VOCABFLOW_API_URL` scheme environment variable.
- `Domain/Practice/`: `PracticeTask` decodes a plan (an unknown template or variant fails the whole plan on purpose), `TaskAttempt` is the pure per-task state that records `TaskEvent`s, and it enforces the rules that would otherwise reject the entire commit with 422.
- `Features/Practice/PracticeSessionStore.swift` runs plan → steps → commit. The commit body is encoded once so retries are byte-identical. Task views are in `Features/Practice/Tasks/`, hosted by `TaskScaffold`.
- Routing: `AuthStore.phase` → `LearnerStore.phase` (`GET /me` decides onboarding) → onboarding → active practice session → active challenge run → sandbox → shell.
- `Features/Auth/`: `AuthView` (log in, password reset by emailed code in two steps) hosts its own `NavigationStack` to push `SignUpView`. New passwords follow `PasswordPolicy` (shown live by `PasswordRuleList`; the backend enforces the same rules). Sign in with Apple, and Google without the SDK (`SocialSignIn.swift`: OAuth code + PKCE in `WebAuthenticationSession`, client ID from Info.plist `GoogleClientID`). Both send an ID token plus the raw nonce to the backend. Change password lives in Settings (`ChangePasswordSheet`). Provider setup (Google Cloud, Apple Developer, Supabase templates/SMTP) is in `docs/AUTH_SETUP.md`.
- **Daily speaking** (backend `docs/DECISIONS.md` "Daily speaking", FRONTEND_FLOW §7.7): `settings.dailySpeaking` (off by default) is `LearningPreferences.dailySpeaking`, set by `DailySpeakingToggle` in onboarding's Routine step (sent only once turned on) and by a switch on the Profile routine card (`LearnerStore.setDailySpeaking`, saved at once; `EditRoutineView` doesn't have it). With it off, Daily has no `recording`. A learned word's recording carries `meaningCue`, which is decoded but not shown: every recording goes straight to the scored read-aloud. A recording's `ipa` (which of the word's sounds to read, e.g. bass /bæs/ vs /beɪs/) is shown under the word by `TaskScaffold`. Speaking never changes progress, and the copy must keep saying so.
- **Scored read-aloud (T7b):** a take scored by the backend (`RecordingAssessment.accuracyScore` set; on-device and Lab takes have none) shows the score ring (`PronunciationScoreRing`) and the band title in the mic's place, colours the prompt word per syllable (`PronunciationColoring.segments`, plain when the syllables don't spell the word), and puts the syllables' detail in the panel (`PronunciationDetail`, expands in place; none for a one-syllable word, whose band the backend sets from `passed`). `band` and `syllables` are optional on decode; without a `band` the client derives one from the score (`PronunciationBand.fallback`, `good` from the backend's pass mark 80). While uploading, the word sweeps (`RecordingPromptStyle.scoring`) and the status reads "Scoring…".
- `Features/PlacementTest/`: `PlacementTestStore` and `PlacementTestView` run the level test, hosted as an onboarding step and as a full-screen cover from `EditLevelView`. No answer key on the client; the backend scores it and saves the level.

### Scope completion, review load, "I know this"
Contract: `vocab-backend/docs/FRONTEND_FLOW.md` §13. Every new field is optional on decode, so an older backend still works.
- **Daily auto-continue:** `PracticeSessionStore` plans the next daily after an all-review plan only when `newWords.withheldReason == nil`. Any reason (scope exhausted, override, review only…) would get the same answer again, so the session ends instead. Don't loosen this; it is what stops a plan loop.
- **Extra plan data:** `SessionPlan` decodes `steps` twice. Once as `[PlanStep]`, and once for the extras (`sourceTopics` by task id, `knownChecks` by check-task id), so `PlanStep` keeps its shape. `reviewWords` feeds the "Review words you've learned" preview with topic labels; without it the store falls back to `ReviewWord.due` from the library.
- **Review only:** `startReviewOnly()` sends `reviewOnly: true` and never continues to new words. Home offers it as "Extra review" when the backlog is above `ReviewLoad.statusThreshold`, and as "Review N words" when the scope is exhausted.
- **"I know this"** (always on; no setting): daily plans (not review-only) send `knownCheck: true` and carry a `known_check` typing task before each Learn card. The app never shows that task. See memory `known-check-on-intro-card`.
  - The check step shows its word's Learn card (`knownCheckOffer`) with "I know this word" below Continue. Continue (`declineKnownCheck`) drops the check and counts the card as learned.
  - "I know this word" (`markKnown`) skips the check, the card and its `skippableTaskIds`, and sends the Learn step id in `knownLearnSteps` (backend §13.6).
  - Skipped tasks and known Learn steps are left out of the commit body. Sending them back would be harmless, but a mismatch is a 422.
- **Home:** the Daily Lesson card is driven by `DailyLessonStatus`, a pure function of `LearnHome`. The card shows only the next session's counts (`sessionReviews` = due capped at `reviewLoad.dueCap`, and new words); scope, lowered-goal and backlog notes sit in the ⓘ popover next to "Today’s session". `ReviewLoadChoiceSheet` opens from Home when `LearnerStore.shouldOfferReviewChoice`: at most once per launch, never during a session. Any way out of the sheet calls `POST /me/review-load/ack`.
- **Follow-up after closing:** a session screen can't present shell sheets, so it calls `close(followUp:)` (`.chooseTopics` or `.randomPractice`). `MainShellView` reads it with `consumeFollowUp()` when it reappears. The Focus editor lives on the Profile stack, so "Choose topics" switches tab first.
- **Topic progress:** `learnedMeanings`/`totalMeanings` come from `GET /catalog/collections`, which `LearnerStore.refresh()` reloads. "Finished" is computed (`Topic.isFinished`), never stored, so new content reopens a topic.
- **Profile:** the Profile tab owns the per-collection review pauses, the auto-balance toggle and cancelling an override.

### Premium and the free plan
Contract: `vocab-backend/docs/FRONTEND_FLOW.md` §16; setup in `docs/PREMIUM_SETUP.md`. The server decides who is Premium (`GET /me` `plan`); the app never grants it locally. `plan.limits == nil` means nothing is limited (Premium, backend flag `FREEMIUM_ENABLED` off, or an older backend).
- `LearnerStore`: `freeLimits`, `isPremium`, `offersPremium`, `canRedeem` (`features.redeemEnabled`), `maxTopics`, `recordingScoring`, `accountToken` (the user id, sent as the StoreKit `appAccountToken`), `adoptPlan`, `redeem(code:)`.
- Topics: `LearningPreferences.toggleTopic(_:limit:)` refuses to add past `maxTopics` (returns false → open `PaywallView(reason: .topics)`); removing always works. `TopicPicker(maxTopics:)` shows "n/x free topics" and only "Clear all". `EditFocusView` won't save a lapsed-Premium scope above the limit. At the limit the unselected chips dim (`TopicChip.isLocked`) but still open the paywall. Collection: a limited learner keeps the saved one (backend `FREE_COLLECTION_LOCKED`); `EditFocusView` dims the others (`LearnerStore.lockedCollectionID`) and opens `PaywallView(reason: .collection)`.
- Words: `withheldReason`/`newWordReason` `free_limit` (`NewWordReason.freeLimit`). `DailyLessonStatus.freeWordsUsedUp` swaps the Daily card for reviews + "Get Premium"; an empty daily with `free_limit` closes with `FollowUp.upgrade`, which `MainShellView` turns into the paywall.
- Speech: `RecordingScoring.onDeviceOnly` (free) never uploads; without recognition the take is `unavailable` (`onDeviceRecognitionUnavailable`). `PracticeSessionStore.scoringForSession` re-reads the plan at every session start; a `403 PREMIUM_REQUIRED` mid-session switches to the device. `isFreeSpeaking` shows the Premium hint under a free take.
- StoreKit (`Features/Premium/`): `StoreKitClient` (`LiveStoreKit`, `NoStoreKit` for previews), `PurchaseStore` (listens to `Transaction.updates` from launch, syncs `currentEntitlements` once the profile loads, sends every verified transaction to `POST /me/subscriptions/appstore` and finishes it only after the server answers, or on `APPSTORE_TRANSACTION_OWNED/INVALID`). Product ids: `PremiumProduct` = backend `APPSTORE_PRODUCT_IDS` = `Syll.storekit`.
- UI (redesign 6.x): Premium identity = the `grape*` ramp (Premium only, nowhere else), Sun 400 as its spark, signature gradient Grape 500 → Coral 400 (`PremiumGradient.accent`, `PremiumWord` adds the shimmer), wash Grape 100 → Grape 50 → Coral 100 (`PremiumGradient.wash`/`PremiumWash`). `ActionButtonStyle.Kind.premium` (Sun 400, Sun 900 label, crown leading) is for Premium entry points and the paywall's pinned action only. `PaywallView(reason:)`, the only colourful screen (Brilliant's layout, Syll's materials; no serif, no Syllie): `PremiumKeyVisual` (fan of word cards), step 1 a Free vs Premium table ordered ✓ rows before ✕ rows with the limit met leading the ✕ rows, a flat Grape 500 Premium column and flat Grape checks; step 2 yearly + monthly plan cards (chosen: Grape 50, Grape 500 border), Coral saving pill only for a real yearly saving (`[PremiumOffer].yearlySavingPercent`). Profile: `ProfileUpgradeCard` (free) or `ProfilePremiumCard` → `PremiumPlanSheet` ("Your plan": manage, restore, redeem) right under the account block; Settings has no Premium group. `RedeemCodeSheet`.
- Ads (`Features/Ads/`, setup in `docs/ADS_SETUP.md`): `AdStore` counts finished sessions (`PracticeSessionStore.onSessionFinished`, not the Lab) in `UserDefaults` and shows an interstitial after every `features.adEverySessions` for learners with `plan.limits`, from `MainShellView` once a session screen closed without a follow-up, never at launch. `AdMobInterstitials` (UMP consent → ATT → SDK start) compiles only with the `GoogleMobileAds` package; otherwise `NoInterstitialAds`.

### Session results (tiles and detail sheet)
Spec: `Spec: Session Result Statistics v1.md`; contract `vocab-backend/docs/FRONTEND_FLOW.md` §15. The server picks every group (from its SRS and speaking-progress decisions); the client never regroups. The skill system is gone (backend `docs/DECISIONS.md` "Skill system removed"): no skill statuses, issues or skill changes anywhere.
- Decode: `CommitSummary` carries `review`/`newWords` (daily) or `practice`/`needPractice`/`countedAsReview` (Random/Weak), plus `speaking` in any mode that scored a recording, all optional. `ResultGroups` reads only known group keys; `ResultSkill` (a task-type label) and `SpeakingStatus` are lenient. The four legacy counts are optional and feed only `LegacyResultGrid` (checkpoint, or a session saved by an older backend).
- Speaking: `speaking_practice` (My Words → Speaking Practice) plans one recording per learned word; its results are the Speaking tile and block only. The sheet's Speaking block lists every scored word from `speaking.groups` (`notPassed`, then `passed`, each with `score` + `band`), then the collapsed status changes; without `groups` (older backend) it falls back to the "Said right: n of m" line.
- Results screen: tiles have no link of their own (every tile opens the same sheet, at its block); one "See session details ›" link under the tile row says so. The word page shows `speaking` (not tried / practicing / fluent, Azure scores) and `needsPractice` (the Weak Words definition: missed recently, latest answer included).
- Daily chain: `PracticeSessionStore.pendingReviewSummary` keeps the first commit's `review`; `finish` merges it into the last summary. `close()` clears it.
- `PracticeResult` (kind + summary) → `ResultTiles` (pure rules, tested by `ResultTileTests`) → `ResultTileView` (one per part with something to show) → tap opens `SessionResultDetailSheet` (`ResultSheetModel` blocks; dates via `ResultDateText` in the learner's time zone). Not to be confused with the demo engine's `SessionResult`.
- Tiles show only a number, a caption and lines naming the weaker groups; a tile with nothing to report is left out, and LP is not a tile (the `SessionEffortCard` below shows it). The proportion bar is on the sheet, one per block (`ResultSheetBlock.bar`), keyed by the swatch (`ResultSwatch`) in front of each group header. Each group has a one-line explanation and each weaker word shows its `cause` (+ `struggledAt`) as sent by the server.
- Random, Weak and Speaking results have "Practice again" (`practiceAgain()` replays the last request). The Practice Lab's "Results screens" section shows `Resources/results_lab.json` fixtures on the real screen.

### Learning journey and content reports
Contract: `vocab-backend/docs/FRONTEND_FLOW.md` §17–18.
- **Journey** (`Features/LearningJourney/`): `LearningJourneyStore` loads `GET /me/learning-journey`. Home's `LearningJourneyCard` (after "Learning") shows the current week; `LearningJourneyView` (`ShellPage.learningJourney`) shows a chosen period. History only: it starts nothing. The shell's `.task` force-refreshes it, so it picks up every commit; a failed load keeps what was shown and never shows zeros. Days are the server's local `yyyy-MM-dd` strings, formatted in UTC by `JourneyDate`. The weekly goal counts sessions, not days. Not to be confused with the old `Features/Journey/` checkpoint path.
- **Content reports** (`Features/ContentReport/`): `ContentReportSheet` via `.contentReportSheet($target)`. A `ContentReportTarget` is captured when the sheet opens: `PracticeSessionStore.contentReportTarget` for the session flag (FlowHeader's right slot, off in the Lab and checkpoint challenge, disabled while the mic is busy), `ReportMeaningLink` in word detail and other meanings (hidden on `edited` meanings). A report never touches the attempt, the session or its commit. `ContentReportStore` resends an unanswered report with the same `clientReportId`.

### Challenge (Match Madness)
- Replaces the Journey/Checkpoint UI (Home card `ChallengeHomeCard`, map `ChallengeMapView` pushed as `ShellPage.challengeMap`). The old Journey files and `LearnerStore` checkpoint/journey loading remain only until the backend migration; nothing user-facing routes to them. Challenge never touches Daily, SRS or `PracticeSessionStore`.
- Wire models live in `Domain/Challenge/ChallengeMapModels.swift` and `ChallengeRunModels.swift`, matching `vocab-backend/docs/FRONTEND_FLOW.md` §12. Unknown enum values decode to `.unknown`. Map levels carry the current goal and star rules for the level sheet; the run plan has the final say.
- `MatchMadnessEngine` is the pure reducer and must equal the backend's `Board`/`replay` (`src/modules/challenge/domain/match-madness.ts`), or commits fail with 422: refill takes the first queued pair whose `word` is neither on the board nor matched in the last `minMatchesBetweenRepeats` matches; event `elapsedMs` strictly increases; `goal_reached` ends at the last event. `ChallengeBoardOrdering` is the shared column order (SHA256 of `seed|correctCount|side|tileId`). `MatchMadnessBackendParityTests` holds a fixture generated by running the backend's code: regenerate it when those rules change. Stars and the official score come only from the server; the plan's `score` rule (incl. `perSecondLeft` clear bonus) drives the live display score, hidden when a plan lacks it.
- The board on screen does not follow the engine's per-match reorder: `ChallengeBoardSlots` keeps tiles in fixed slots, a matched pair shows correct for `MotionTokens.matchCorrectHold`, then fades and the next pair fades into the freed slots. Commits carry tile IDs only, never positions. Match tiles (here and in `MatchTaskView`) share `Spacing.matchTileMinHeight` and grow to the tallest tile.
- `ChallengeRunStore`: issue → ready → start (the monotonic clock starts only after `POST …/start` answers) → playing (never pauses; `tick()` on foreground ends a run as `time_up`) → commit (body frozen once, retries are byte-identical, `PendingRun` in `UserDefaults` lets the next launch settle a killed run) → results. `startSandbox` runs a static plan on the same engine for the Practice Lab (timed and untimed), with no API calls. `ChallengeMapStore` refreshes after every settled run and when the shell appears.

### Two independent demo engines
The scored session below is no longer reachable from the UI; Home and My Words start backend sessions instead.

1. **Scored session** (Learn → Build → Recall → Results)
   - `Domain/Learning/SessionReducer.swift` is a pure reducer: `(SessionState, SessionAction, DemoContent) -> SessionTransition(state, events)`. Invalid action/phase combos return `.unchanged`. All scoring rules live here and are what the tests target.
   - `Features/SessionStore.swift` is a thin wrapper: intent methods → `send(action)`, then maps `SessionEvent`s to side effects (haptics, `sessionToken` rotation on restart, `onFinish` → `ProgressStore`).
   - `Features/SessionFlowView.swift` keeps one persistent frame (header + pinned action bar) across all Learn/Build/Recall steps; only stage content transitions. Per-step UI input (selected tile, typed text, drag state) lives in `FlowDraft`, which is *not* part of scored state and is reset before every advance.
2. **Practice Lab** (sandbox, unscored)
   - Lab entries mirror the seven backend task templates (`TaskTemplate`: select, clozeSelect, typing, flyReorder, match, surgery, recording). `Resources/practice_lab.json` holds example tasks in the plan wire format; `LabLibrary.validate()` requires every template to be present.
   - `Features/PracticeLab/TemplateSandboxStore.swift` owns Lab navigation and its own `PracticeSessionStore` running in sandbox mode (`startSandbox`): same task views via `PracticeTaskView`, no planning, assessment or commit. It is a separate instance from the live session store, injected into the Lab subtree by `LabTaskView`.

Adding a template touches the backend contract (`TaskTemplate`, `TaskAttempt`, a view in `Features/Practice/Tasks/`, `PracticeTaskView`) and a `practice_lab.json` entry.

### Content pipeline
- `Resources/demo_words.json` (words, build challenges, recall prompts, intro motion config) and `Resources/practice_lab.json` (Practice Lab example tasks).
- `DemoContentRepository` decodes → validates (`ContentValidator` / `LabLibrary.validate`) → shuffles options deterministically from the JSON `seed` (`DemoSeed`). Invalid content is a `fatalError` at launch, so any JSON edit must keep validators passing; `ContentValidationTests` and `LabLibraryTests` load the real bundled files.

### Design system and motion
- **Keep three sources in sync:** the app, `docs/app-redesign-v1.html` (screens by flow) and `docs/DESIGN_SYSTEM.md` (rules). Any UI change updates whichever of the two docs it touches in the same change; when they disagree, the app wins and the docs are corrected.
- `DesignSystem/Tokens/` (colors, spacing, radii, typography, motion) — use tokens rather than literal values. App is forced to light mode. The visual spec is `docs/app-redesign-v1.html`: `Colors.swift` holds its five ramps (`ink50…ink950`, `blue*`, `green*`, `coral*`, `sun*`) and the semantic names map onto them.
- Every card border is `Borders.card` (2 pt, Ink 200, radius 20, no shadow), selected or not (option rows, panels, `CardSurface`); selection changes only the colour. Rows inside a card are split by `CardDivider` (1.5 pt Ink 100). Word tiles/keys with a depth edge, text fields, buttons and chips keep their own widths.
- Buttons are 50 pt capsules (`Spacing.buttonHeight`). `PrimaryButton` is Ink 800 on an Ink 950 depth edge everywhere, practice included (Check, Continue, Save); Blue `.practice` only for actions that start practice (Home "Continue", "Practise now"), passed explicitly. `SecondaryButton` takes its kind from the `actionContext` environment (`.practice` is set in `AppRootView` on session, challenge and Lab task screens): white `.outline3D` with a depth edge there, flat `.outline` elsewhere. Green `.success` / Coral `.retry` appear only in the feedback panel; `DestructiveButton` is flat Coral 600. `.plain` (ink text, no fill/border/edge) is for a low-key extra action such as "I know this word".
- iOS default controls are replaced by `DesignSystem/Components/Controls.swift`: `SelectChip`, `StatusPill`, `IconButton` (36 pt round Ink 100), `IconBadge`, `ScreenTitle`/`SheetTitle`/`SectionTitle`, `.fieldSurface`. Toggles, segmented controls (`SegmentedControl` wraps the iOS `Picker(.segmented)`), the tab bar, pushed pages' back button, the Profile gear and every close/back button (sheets: `SheetCloseButton`/`SheetBackButton`; bar-less screens: `BackButton`, `CloseRunButton`; the session/Lab/placement `FlowHeader` ✕ is a bare Ink 400 icon, no circle) stay system-default (`Toggle`, `TabView`, `iconOnlyBackButton()`, `SystemBarButtonLabel`: Liquid Glass on iOS 26+, a bare ink icon before). Confirmations use `ConfirmSheet` (a short fitted `.sheet` with visible Cancel and Confirm) instead of `.alert`; swipe actions and context menus become a ⋯ button opening an action sheet.
- All animation goes through `MotionCoordinator` (`@Environment(\.motion)`), which honors both system Reduce Motion and the in-app setting. Use `motion.perform(...)`, `motion.travel(...)`, `motion.stepTransition`, etc. instead of raw `withAnimation`/transitions.
- Syllie (`DesignSystem/Components/SyllieView.swift`): artboard `Syllie` (the original black Syllie, V1. The file also holds Periwinkle V2 copies — `SyllieV2`, `LoadingV2`, `CelebrateChallengeV2`, `CelebrateSessionV2`, `HomeSyllieV2`, with the same timelines, state machines and view models — which the app does not play; switching to them is only the artboard names in code plus re-rendering `AppIcon-1024.png`), state machine `Syllie`, view model `Syllie` with `mood` (enum `Mood`: idle, happy, excited, thinking, oops, sleepy, the happy variants happyPop/happyWiggle/happyPuff/happyFloat/proud and the oops variants oopsSquish/oopsWobble/oopsFreeze/oopsSlip — mirrored by `SyllieMood`; `thinking` and `deepThoughtHold` are loops, the rest are one-shots; `deepThought` (timeline `deep_thought_in`, 2 s: one eye squints, the other looks up-right, head cocked, the top-right lobe throbs; no props, and no inward-slanted eyes, which read as angry) ends on the pose `deepThoughtHold` (`deep_thought_hold`, 3 s: lobe throbs, then the eyes swap sides and back) loops on; `SyllieReactionView` switches to it via `SyllieMood.settledMood`, because an Any State transition back to the intro would keep firing) and `react` (trigger, replays the current mood). State machine `Syllie` has a second layer `Snore` that plays the rising "z" marks (`SnoreZ1-3`, hidden by default so other state machines never show them) only while `mood == sleepy`. `Syllie` also has state machine `LoadingFly` (layers `Fly` + `Blink`: body stretch, lobe lag, blinking). The `Loading` artboard (state machine `Loading`) nests Syllie running `LoadingFly` and adds the wind lines and bob; `SyllieLoadingView` plays it. The `Celebrate` artboard (390×844, state machine `Celebrate`: fly-in, landing, double bounce, then `hold`) nests Syllie running its own `Celebrate` state machine (`celebrate_face` → `celebrate_sway`, a happy left/right sway loop); `SyllieCelebrationView` plays it on the Challenge results (confetti at `confettiCue`, ~1.1 s). The end of a practice session is two beats (`SessionFinishView` in `PracticeSessionView`): `SessionCelebrationView` on the `CelebrateV2` artboard (390×844, state machine `CelebrateV2`, view model `CelebrateV2`: enum `variant` puff/fireworks/flip/loop/bounce, enum `kind` session/collection, bool `perfect`, trigger `play`; values are set before the state machine starts because the entry transitions read them; the variant is random and never the last one, and the copy appears at `CelebrationVariant.landing`), then `PracticeResultsView` ("Summary"). `docs/app-redesign-v1.html` plays the same artboard with the Rive web runtime; after re-exporting the `.riv`, regenerate `docs/syllie-riv.js` (command in the doc's `<head>`). On Home, `LessonMascot` uses its own artboard `HomeSyllie` (520×560, state machine `HomeSyllie`, view model `HomeSyllie` with `scene`, enum `HomeScene`: idle, sleepy, wakeUp, playLetters, planeChase), played by `HomeSyllieView` / `HomeSyllieScene`. It holds a separate copy of Syllie's shapes (under `Stage`, offset 130 down so the props have room above) plus the `Letter` tile and `Plane` props (blue, `interactive` tokens), and its own timelines (`idle`, `sleepy`, `wake_up`, `snore_bubbles`, `snore_off`, `play_letters` 5.5 s, `plane_chase` 5.0 s: the plane flies in, does one loop (radius 75) over Syllie's head and exits right, sampled every 4 frames as linear keys, rotation following the heading; travel keys use linear or ease-in/out cubic params, not the default cubic, which stops the prop at every key; every timeline keys both props' start pose and opacity 0 on frame 0, so a replay doesn't blend in from where the prop last stopped) — editing the `Syllie` artboard does not change it. It loops: a short idle (`idleBeat`), one random play scene, `sleepy` for `sleepBeat` (layer `Snore` shows the z marks), `wakeUp`, and round again; a tap wakes him early. With reduced motion he skips the play and stays asleep until tapped. The launch `SplashView` shows only Syllie (no wordmark), playing the `loading_blink` timeline on the `Syllie` artboard through the legacy `RiveViewModel`, since the `Syllie` state machine has no blink-only mood. `ReviewPreviewView` (the session's "Words to review" step) puts Syllie between the intro text and the word list: while the words fly in he loops `reviewWatch` (eyes down at the list, scanning left to right; each 1.6 s loop starts and ends with the eyes centred), starting as the words start flying; the entrance (`entranceTiming`: stagger stretched/shrunk from `MotionTokens.reviewTileStagger`/`reviewTrainStagger`, plus a short lead) is timed so the last word comes to rest (`reviewTileSettle`/`reviewTrainSettle`) after a whole number of loops (`SyllieMood.reviewWatchLoop`, at least one), and then he plays `reviewReady` once (one nod, starting from that pose), then idles. `ReviewFinishedView` (review done → new words) replaces the checkmark with Syllie playing `reviewToLearn` (timeline `review_to_learn`, 1.2 s: proud puff, look down at the list, eager stretch) once, then idle. In practice, `TaskScaffold` puts Syllie beside the action (`FeedbackActionPanel(mascot:)`): a random `SyllieMood.thinkingMoods` loop (`thinking` or `deepThought`, re-picked per question and after "Try again") while answering, a random `SyllieMood.happyReactions` variant when solved, a random `oopsReactions` variant when wrong/exhausted (both start only after the answer's own animation, `MotionTokens.answerFeedbackSettle`; until then he keeps thinking), and `SyllieReactionView` returns him to idle after the one-shot (`SyllieMood.reactionDuration`, nil for held moods; keep in sync with the timelines). The happy/oops variant timelines, `idle` and `thinking_wait` key the full rest pose (root x/y/rotation/scale, eyes, eye corners, top-right lobe vertices) at their first and last frame, so an interrupted mood can't leave a stray pose; a new mood timeline should do the same. Rive only exports artboards marked as Component, so any new artboard must be one. The `.riv` is built in the Rive editor (cloud file still named "inky", so its export comes out as `inky.riv`: save it as `Resources/Animations/syllie.riv`); keep these names stable.
- Haptics go through the `FeedbackProviding` protocol (wrapped by `SettingsAwareFeedback` so the user setting applies); speech through `SpeechProviding`.
- Learn-stage word intros use six motion recipes in `Features/Learn/MotionTemplates/`, selected per word by `intro.templateID` in `demo_words.json` and hosted by `IntroMotionHost` (presentation only — never affects scoring or advancement).

### Persistence
Tokens live in the Keychain (`KeychainTokenStore`). Otherwise `UserDefaults`: `ProgressStore` (demo run history), `AppSettingsStore`, `LearningPlanStore` (via `PreferencesStoring`, plus `ReminderScheduling` for notifications). Each accepts an injectable/nil `UserDefaults` or in-memory implementation for tests and previews.

### Localization
User-facing strings use `LocalizedStringKey` and live in `Resources/Localizable.xcstrings`. Learning content (Vietnamese meanings, feedback) comes from the JSON files, not the string catalog.

**Rule: every displayed text that doesn't come from data (JSON content, backend responses, user input) must be localized** — UI labels, buttons, titles, errors, accessibility labels/hints/values, VoiceOver announcements, notification text.
- View-facing parameters take `LocalizedStringKey`, not `String`. Where a `String` is required (stores, errors, `StreamingText`, models), build it with `String(localized: "…", bundle: .appLanguage)`; without the bundle it ignores the language chosen in the app.
- The display language (`AppLanguage`: the device's language via `AppLanguage.device` until one is picked in Settings; there is no language step) applies live: `AppRootView` sets `\.locale` and rebuilds the screen, and `Bundle.appLanguage` serves `String(localized:)`. Formatters outside `Text` take `AppLanguage.active.locale`.
- `Text(verbatim:)` / `Text(someString)` only for data, numbers/counters, or the brand name.
- Every new key must be in `Localizable.xcstrings` (Xcode syncs it on build; `xcodebuild` does not). Check with the compiler's `.stringsdata` output when in doubt.
- **Every supported language is mandatory.** The list is `AppLanguage.allCases`; the target markets are in `docs/LOCALIZATION_MARKETS.md` (`vi`, `en`, `hi`, `es`, `ja`, `pt-BR`, `ko`, `zh-Hant`, `th`, `ar`, `id`). Every displayed text, in `Localizable.xcstrings` and `InfoPlist.xcstrings`, needs a translation (state `translated`) in **all** of them in the same change. A key missing one language is a bug. Multi-argument strings use positional specifiers (`%1$@`, `%2$lld`). Plural strings carry the CLDR categories each language needs (Arabic: zero/one/two/few/many/other). Info.plist strings (permission prompts) live in `Resources/InfoPlist.xcstrings`.
- Adding a language: a case in `AppLanguage` (raw value = the `.lproj` name, `nativeName`, `uiLocale`, `layoutDirection`), its code in `knownRegions` of `project.pbxproj`, and a translation of every key. Arabic is right-to-left: `AppRootView` sets `\.layoutDirection`, so layouts must use leading/trailing, never left/right.
